# Air-gapped dependency mirroring

Nothing in the production build or runtime path may reach the public
internet. This document lists exactly what has to be mirrored internally
and where the connected-build-only shortcuts live in the repo, so they can
be found and replaced before a real air-gapped build.

## Python interpreter

The backend image (`Containerfile`) fetches a
[python-build-standalone](https://github.com/astral-sh/python-build-standalone)
CPython 3.13 tarball over HTTPS at build time (`ADD https://github.com/...`)
because UBI9's RPM repositories don't yet ship Python 3.13 (see
`docs/adr/` for why UBI9 + a standalone interpreter was chosen over
dropping to 3.12). For an air-gapped build:

1. Download the exact asset once, on a connected machine:
   `cpython-<PYTHON_VERSION>+<PYTHON_BUILD_STANDALONE_RELEASE>-x86_64-unknown-linux-gnu-install_only.tar.gz`
   (versions pinned as `ARG`s at the top of `Containerfile`).
2. Publish it to an internal artifact store reachable from the build
   cluster.
3. Replace the `ADD https://...` line with
   `COPY python-3.13.tar.gz /tmp/python.tar.gz`, sourced from that internal
   store (e.g. via a build-context fetch step, not a hardcoded internet
   URL).

## Python packages

`requirements.txt` and `pylock.toml` (repo root) are both generated by:

```bash
uv export --format requirements-txt --no-dev --no-emit-project -o requirements.txt
uv export --format pylock.toml       --no-dev --no-emit-project -o pylock.toml
```

Both are hash-pinned and exclude the local project itself (`--no-emit-project`
— the app's own source is `COPY`'d into the image separately, never `pip
install`'d). To populate an internal PyPI mirror:

```bash
pip download -r requirements.txt -d ./wheelhouse --no-deps
```

then point the mirror's index at `./wheelhouse` and build with
`pip install --no-index --find-links=<mirror> -r requirements.txt` — the
exact pattern already used by this team's Ansible-deployed services
(`pip install --no-index --find-links={{ local_mirror }}`), extended here
to a container build rather than a venv-on-a-VM.

Re-run both export commands (and re-mirror) whenever `pyproject.toml`
changes; a stale `requirements.txt` is a silent drift risk.

## npm packages

`frontend/package-lock.json` is committed and hash-pinned by npm itself.
For an air-gapped build:

```bash
cd frontend && npm ci --offline
```

against an internal npm registry mirror (e.g. Verdaccio, or a static
tarball cache) that has pre-fetched every package in the lockfile — `npm
ci` refuses to resolve anything not already in the lockfile, so the mirror
only needs exactly what's listed there, not the whole npm registry.

## Container images

**`deploy/air-gapped-images.txt`** is the full, current list — the two
published application images (`server-scan-api`, `server-scan-frontend`),
the UBI base images each is built from, and the local-dev-only MongoDB/
Redis images — with why each one is needed and whether it is required
for deployment or only for building the images yourself. Keep that file
in sync with `Containerfile`, `frontend/Containerfile`,
`.github/workflows/ci.yml` and `scripts/dev-up.sh` rather than
duplicating the version pins here.

All UBI images pull from Red Hat's registry, which is mirrorable via a
standard Red Hat registry sync (`skopeo sync` or an internal Quay/
Artifactory proxy) under the same subscription/EULA terms as any other
UBI usage. `docker.io/library/mongo` and `docker.io/library/redis` are
dev-only and never appear in the production image or the deploy
manifests — see `deploy/README.md` for why production MongoDB/Redis are
this chart's caller's problem, not this repo's.

## What's still open

This is the initial pass (Phase 1, slice 0). Not yet documented here:
concrete internal-registry hostnames (site-specific, added when a real
target environment is known), a CI job that fails the build if
`requirements.txt`/`pylock.toml` drift from `pyproject.toml`, and a
scheduled process for re-mirroring on a cadence rather than ad hoc.
